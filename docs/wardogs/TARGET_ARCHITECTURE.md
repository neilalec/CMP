# CMP ↔ WARDOGS target architecture and reuse audit

Design audit, 2026-09-23. This remains an incremental target. The implemented slice includes [observation/capability contracts](../../backend/services/game_server_contracts.py), a [read-only WDRCON client](../../backend/integrations/wardogs/client.py), the [generic adapter boundary](../../backend/services/game_server_adapter.py), and a [WARDOGS adapter](../../backend/integrations/wardogs/adapter.py). Public queue acceptance now creates a persisted three-faction lobby and attempts transactional allocation of a compatible WARDOGS server. Verified player join behavior remains open. Missing natural-end/winner evidence **does not block** a useful WARDOGS product, because the result can require a referee. Read the [capability matrix](CAPABILITIES.md) for the narrower status of each actual WDRCON operation. The WARDOGS [frontend feature](../../frontend/src/features/wardogs/) keeps isolated mock scenarios and can opt into an authenticated backend read.

## What the repository does now

`backend/app.py` uses Flask-SocketIO with Eventlet; `backend/wiring.py` exposes HTTP and socket routes. `backend/services/queue.py` and `backend/matchmaking.py` accept queues and build two-team lobbies. `backend/app_core.py` selects per-server callbacks and passes them into `backend/services/live_roll.py`. Those callbacks use the Squad-specific HTTP client/normalizers in `backend/services/bridge.py`, the registry in `backend/services/server_registry.py`, and the bundled `squadjs/bridge-server.js` plus `squadjs/cmp/` modules. `live_roll.py` expects Squad layer transitions, two-side roster enforcement, and a winner/loser ticket record from `/round/best`; `app_core.save_completed_match` immediately invokes `backend/services/elo.py`. This is *not* a generic server adapter today.

`backend/services/state_persistence.py` serializes lobbies as JSON but restores only `team1` and `team2`. `backend/services/history.py` stores JSON team/result fields but its scored filter requires winner/loser tickets. `backend/app_state.py` declares `NvN` queue modes, two-team capacities and Squad map pools. `frontend/src/views/Lobby.vue`, `frontend/src/views/Results.vue`, `frontend/src/stores/state/lobbyState.js`, and `frontend/src/features/lobby/` consume the two-side contract. The WARDOGS feature instead has its own Match → Factions → Groups → Players model and local mock source.

## WARDOGS rating policy and implementation boundary

`backend/services/wardogs_results.py` owns explicit admin confirmation and correction. `wardogs_result_revisions` has a revision ID, lobby ID, monotonically increasing revision number, superseded revision ID, status, three scores, optional winner faction, actor, timestamps and provenance. The newest revision is authoritative. This store and `wardogs_lobbies.roster_json` are separate from Squad `completed_matches`, `users.elo_rating`, and `elo_match_updates`; WARDOGS rating storage and match-room UI are game-specific. Registered lobby player IDs are CMP account names today; Steam ID is a separate server-observation identity and must not be used to reconcile competitive membership.

The chosen policy is individual pairwise multiplayer Elo, calculation version `wardogs_rating_v1`. For faction `i`, its pre-match strength `R_i` is the arithmetic mean of its registered planned active players' current WARDOGS ratings. Reserves are excluded. Each pair has expected score `E_i = 1 / (1 + 10^((R_j - R_i)/400))`. Its actual score `S_i` is 1 for a higher authoritative placement, 0 for a lower placement, and 0.5 for an authoritative tie. The unrounded per-player delta for a faction is the sum, against the other two factions, of `24 * (S_i - E_i)`. Ratings for every faction and pair are read from the same pre-match state; applying one pair never changes the next pair's expectation. Score margins are ignored.

Candidate comparison: pairwise Elo extends the already understood CMP expected-score model into three explicit pairings and gives a transparent rule for ties; it is deterministic, easy to audit, and needs no population-wide fit. Placement-based multiplayer Elo models rank directly, but adds rank/tie weighting rules that are less familiar and less directly reusable. TrueSkill can model uncertainty and team skill, but introduces priors, variance updates and more state to explain and replay for a small beta. Custom placement points are easiest to explain, but give the same change to expected and surprising outcomes and do not adapt to player strength. Pairwise Elo is the least complex choice that still accounts for expected result and supports each faction pair symmetrically.

Each rated result must have three complete planned active factions with the same nonzero player count, and every planned active player must resolve to a registered CMP identity. This matches the current `wardogs_beta9` mode (three active players per faction, no reserves) and makes equal per-player faction deltas conserve total points before rounding. Until an explicit unequal-roster policy exists, incomplete, unresolved or unequal rosters are ineligible as a whole. Only registered planned active CMP identities receive deltas, regardless of actual connection or observed faction. Reserves, unexpected players and live observations do not add or remove recipients. A player who never joined the server still receives the result for their accepted planned active slot. Replacement/substitution is unsupported by the current lobby flow; later substitutes require a new authoritative roster rule. Premades do not change K, expected strength, or per-player treatment; parties and clans have no rating.

Worked examples below show faction rating changes; every eligible active player in a faction receives that faction's rounded change (subject to the match-wide one-point conservation correction). `K=24` is used independently for each pair:

| Pre-match faction ratings and authoritative placement | Expected-score arithmetic | Final faction deltas |
| --- | --- | --- |
| A=1000 first, B=1000 second, C=1000 third | A: `24×(1−.5) + 24×(1−.5)`; B: `24×(0−.5) + 24×(1−.5)`; C loses both | A `+24`, B `0`, C `−24` |
| A=1200 third, B=1000 first, C=800 second | A: `24×(0−.760) + 24×(0−.909)`; B: `24×(1−.240) + 24×(1−.760)`; C: `24×(1−.091) + 24×(0−.240)` | A `−40`, B `+24`, C `+16` |
| A=1000 and B=1000 tied first, C=1000 third | A/B tie contributes 0; each beats C for `24×.5=12`; C loses twice | A `+12`, B `+12`, C `−24` |
| A=1000, B=1000, C=1000 all tied | Each pair contributes `24×(.5−.5)=0` | A `0`, B `0`, C `0` |
| A=1200 first, B=1000 second, C=800 third (favored order) | A: `24×(1−.760) + 24×(1−.909)`; B wins over C and loses to A with equal and opposite expectation residuals; C loses both | A `+8`, B `0`, C `−8` |

A two-way tie for second is A first with B and C tied: at equal ratings, A receives `+24`, while B and C each receive `−12` (their mutual tied pair contributes zero). The examples use unrounded expectations for calculation; displayed decimals are explanatory only.

Starting rating is 1000, fixed K is 24 per faction pair, no provisional factor applies, and there is no zero floor. For stable integer ratings, calculate all deltas at full precision, round to the nearest integer with exact halves away from zero, then correct any match-wide rounding residual one point at a time to conserve the match total. Apply each necessary one-point correction to the faction whose rounded delta moved furthest in the correction direction from its raw delta; ties use canonical faction order (`valkyra`, `lonestar`, `manticore`). Every active player on that faction gets the same delta. Persist and expose the final integer delta, so replay does not depend on floating display values. Three-way placement is represented as three pairwise outcomes: first beats second and third; second beats third. Tied placements produce 0.5 only for the tied pair. A tie for second therefore gives first a win over both others and a tied result between second and third. A three-way tie produces three half results and zero net change.

The result contract now stores complete `placementGroups` directly in each revision. Validation requires all three canonical factions exactly once, nonempty ordered groups, and scores consistent with equal-within-group and strictly-descending-between-group placement. The admin API requires explicit groups for each new completed result and correction; the compatibility `winnerFaction` is derived from a sole first-place faction. The participant DTO and admin history expose placement groups. This forms the direct contract `confirmed scores + explicit placement → result revision → wardogs_rating_v1 consumer`; that consumer must read placement groups and never sort scores. A legacy completed row that cannot be safely converted keeps its original revision and exposes `placementUnavailable` for admin review.

Only the current authoritative revision with status `completed_win` or `tie`, complete authoritative placements, and an eligible roster can rate. Unconfirmed, incomplete, abandoned, void, cancelled, missing-placement and ineligible-roster cases produce no rating event. A status correction to `void` removes that match and requires replay of later ratings. Observed scores may be provenance or admin prefill only; they are never rating inputs.

Corrections require full deterministic replay from the initial value across current authoritative result revisions in chronological match order, rather than applying a second delta to the corrected head. Order matches by the original revision-1 confirmation timestamp (so corrections retain their place), then stable lobby ID; use stable CMP player/faction ordering within each calculation. A replay reconstructs each participant's prior WARDOGS rating, replaces the corrected outcome's effect, and recomputes every later rated match. Reprocessing the same current revision and calculation version is a no-op. Replay after restart yields the same state. Do not backfill historical WARDOGS results automatically when introducing the consumer; the first rating-storage startup saves an immutable activation timestamp; only results whose original confirmation is at or after it can rate.

Persistence keeps immutable per-player ledger events with at least: `event_id`, `replay_generation_id`, `lobby_id`, `result_revision_id`, `player_id`, `rating_before`, `rating_after`, `delta`, `calculation_version`, and `created_at`. A unique key permits one event per generation/lobby/player. Replays append a new generation and new events; a generation record links its predecessor and the active-generation pointer selects the current projection. Keep superseded-generation events intact, rather than editing or reversing them in place. A materialized current-rating row is a rebuildable projection of the active generation, not the audit source. Run replay, ledger writes and active-generation switch transactionally. The consumer must have no call from generic `save_completed_match` and no route to `backend/services/elo.py`.

The authenticated WARDOGS match read exposes the viewer’s current rating and current-generation event for that lobby; the match room shows the rating and signed delta when rated. Keep Squad Elo visibly separate; do not add tiers or a WARDOGS leaderboard as part of the rating consumer. A leaderboard may later query current WARDOGS ratings with its own participation/eligibility presentation policy.

Material v1 abuse risks are managed by the input boundary and audit, not extra formula knobs: repeated premade farming and repeated opponents remain possible, so defer opponent-avoidance and monitor concentration; coordinated throwing can distort three placements and is not solved by Elo; a small population makes estimates volatile, so keep K fixed and expectations simple; new accounts start at the common 1000 with no provisional boost, limiting accelerated gains; result admin abuse remains possible, so retain actor, reason, revision and replay audit; disconnecting does not remove an accepted active player's rating responsibility. Do not add party penalties, disconnect multipliers, or score-margin bonuses without evidence.

Implemented sequence: (1) add authoritative full placement groups to result revisions and admin DTOs, preserving append-only corrections; (2) add a WARDOGS-only pure deterministic calculation service and unit examples; (3) add the versioned event/replay-generation ledger and transactional replay consumer called only after authoritative revision changes; (4) expose current WARDOGS rating and per-match delta separately from Squad profile fields. The focused `backend/services/wardogs_rating.py` service runs inside the result confirmation/correction transaction. No generic rating framework, Squad change, leaderboard, historical backfill or WDRCON result inference is needed.

## CMP competitive workflow reuse audit

The shared path is CMP identity and persisted party → game-scoped queue mode → existing pending-match acceptance/cancel flow → accepted-player snapshot → game/mode-specific assignment and lobby builder. `backend/services/queue.py` handles mode-keyed player lists, queue payloads, cancellation and acceptance without team semantics. At the finalization branch, an internal WARDOGS mode with explicit assignment configuration calls the snapshot builder, matcher, and lobby insertion. No second pending-match system is used.

CMP parties persist a code, leader and members in `active_groups`; group handlers prevent joins while queued and coordinate queue removal/cancellation on leave. The pure `build_wardogs_matchmaking_input` service accepts the eligible players, CMP group maps, safe profile fields, accepted match ID and queue mode. It requires the supplied queue catalog to identify that mode as WARDOGS; the production catalog still has no WARDOGS mode. It returns an immutable input: a valid party contributes its accepted subset once; one accepted member becomes a solo; a party leader is retained only when accepted. Stale mappings, missing groups, malformed groups, and conflicting memberships make affected players solos. It never imports mutable state references, includes unaccepted users, or infers WARDOGS clan/squad type. The internal finalizer consumes this snapshot before assignment.

Queue mode IDs remain globally unique and current Squad IDs are unchanged. Each configured mode carries `game_type`; missing legacy metadata means Squad, while unknown game/mode pairs fail validation. Queue status includes game identity. Squad acceptance retains its server-capacity gate; the WARDOGS beta mode forms a nine-player pending match without requiring a server, then allocates after successful lobby persistence. Queue rows persist mode IDs; unknown or removed IDs are skipped with a warning on restore. Pending acceptance remains process-local: startup clears it and retains valid queued players as unaccepted, with no timer resumed. The frontend queue store merges the server-supplied WARDOGS mode.

The WARDOGS `wardogs_lobby` service persists and validates its three-faction/group/role/readiness read model. The internal finalizer now builds the immutable accepted-player snapshot and stores a complete Hybrid assignment, but no enabled WARDOGS queue starts acceptance. An unclassified party stays `premade`; explicit product metadata must later distinguish squad from clan. Production queue/match capacity policy remains open. WARDOGS does not use Squad `assign_teams`, map vote, lobby restore, live-roll or connection-detail assumptions.

## Minimal integration boundary

The first registry slice is now in `backend/services/server_registry.py`: existing rows migrate to `game_type='squad'`; WARDOGS records use `game_type='wardogs'`, the existing `bridge_url` as a **credential-free WDRCON origin**, and `wdrcon_secret_env` naming a server-side `CMP_WARDOGS_RCON_*` variable. Registration and probe require that variable to be configured; the password is never stored in SQLite or returned by an API. The existing `bridge_token_encrypted` field is **not** reused for WARDOGS: its `itsdangerous.URLSafeSerializer` provides signing, not confidentiality. Changing legacy Squad credential storage is separate work. WARDOGS registration/testing is restricted to admin endpoints; the existing Squad submission flow remains available. Lobby reads expose only the verified dynamic Join ID and player instructions, never an admin origin or credential.

For now, an administrator configures the secret in the backend process environment, then sends `{"game_type":"wardogs","display_name":"...","bridge_url":"https://host.example:7776","wdrcon_secret_env":"CMP_WARDOGS_RCON_SITE_A"}` to the existing authenticated `POST /api/admin/servers/test` and `POST /api/admin/servers` endpoints. The same admin health-check endpoint probes a registered record. The current frontend submission form remains Squad-oriented; no WARDOGS form or player-facing join link is implied by these backend APIs.

WARDOGS health reads only `/v1/capabilities` and `/v1/status`. The registry's `metadata_json` holds a sanitized normalized `capabilityStates` snapshot, build, limits and observation time. A successful status read is `observed`; players/rotation remain merely `advertised` until separately read; mutations stay `advertised` and lifecycle stays `unknown`. On probe failure the current health becomes `offline` and no fresh capability claim is made. The Squad boolean capability columns and health responses are unchanged. Default availability, pool capacity and allocation select only Squad records; the explicit WARDOGS allocation branch is invoked only after WARDOGS lobby creation or an admin retry. The old single global-Squad fallback capacity remains when no Squad records exist.

`backend/services/game_server_adapter.py` now defines the `GameServerAdapter` observation protocol, a control-operation vocabulary, a safe adapter error, and `capability_is_usable`. Reads require an observed state to be reported as usable; controls require effect verification; lifecycle claims require semantic verification. A read may be called before it is observed because its successful call establishes that confidence. `WardogsAdapter` wraps `WDRCONClient` for capabilities, status, players, rotation and conservative lifecycle observation. It has no write dispatch. Its `require_control` gate rejects advertised-only operations and still rejects a verified operation because no WDRCON write implementation exists.

`server_registry.get_game_server_adapter_for_server` selects `WardogsAdapter` for a persisted `game_type='wardogs'` record using the existing restricted environment credential reference. It returns `None` for Squad, which explicitly means the existing `app_core.py` callbacks and `bridge.py` remain the active path. Unknown game types fail safely. A Squad wrapper/migration is optional later if a concrete call site needs one; there is no reason to force Squad through an incomplete adapter now. WARDOGS matchmaking/orchestration remains separate from this transport boundary.

Suggested typed contract (design notation, not code to introduce in this audit):

```text
capabilities() -> {name: {level, build, checked_at, evidence_ref}}
observe_status() -> ServerStatus(server_id, observed_at, health, map_config?, scores?, player_count?)
observe_players() -> [ServerPlayer(steam_id?, name?, observed_faction?, observed_at)]
observe_rotation() -> RotationSnapshot?                 # optional
request_control(command, actor, idempotency_key) -> CommandResult(requested, acknowledged,
                                                       observed_effect?, error?)
observe_lifecycle(cmp_attempt_id) -> LifecycleObservation(
    state=unknown|live_observed|completed_authoritative,
    source, observed_at, server_round_id?, final_result?)
```

`ServerStatus` and `ServerPlayer` are observation DTOs, not the CMP match model and not raw WDRCON objects. The CMP match holds faction IDs, group membership, active/reserve assignments, registered profile IDs and explicit player readiness; reconcile observations by validated Steam ID. Scores are timestamped and may be absent. `LifecycleObservation.unknown` is a first-class answer. `completed_authoritative` requires an independently established server result and round identity; no current WARDOGS evidence enables it. A `CommandResult.acknowledged` response never implies `observed_effect` or final result. Control methods are optional and must be checked by per-build capability *and* CMP permission; absence returns an unsupported/degraded result, not a fake success.

The contract prevents WDRCON JSON from leaking into CMP application state. `bridge.py` continues translating Squad `steamID`/numeric `teamID`, layer fields and `/round/best` through the existing Squad callbacks. WARDOGS maps Steam strings, named factions and status/rotation independently. The rating consumer reads only the stored authoritative result revision and CMP planned roster, never a WDRCON object.

## Implemented WARDOGS application-state seam

`backend/services/wardogs_lobby.py` stores versioned CMP-owned WARDOGS lobby JSON in a dedicated SQLite table. The service validates exactly three canonical factions, stable group/player IDs, solo/premade/squad/clan group type, active/reserve role, optional leaders/commanders, and explicit readiness. The internal finalizer creates these planned rosters from CMP identity snapshots, including a neutral `premade` type and pending-match/configuration provenance. It inserts only after complete assignment and validation; the insert cannot overwrite an existing roster. A retry with the same roster/configuration returns that lobby, while a conflicting retry fails. The record is durable across restart and separate from the Squad `active_lobbies` table.

One Flask-SocketIO background task scans persisted WARDOGS allocations every 20 seconds and reads only normalized `WardogsAdapter.get_status` and `get_players`. The flow is allocated lobby → read-only poll → process-local normalized observation → Steam-ID reconciliation → authenticated read model and private Socket.IO update notice → frontend HTTP refresh. A unique, valid Steam ID is the only automatic reconciliation key. Planned faction and readiness never change from observation. A successful empty roster marks linked players disconnected; unknown identities remain unreconciled. Unmatched or ambiguous players stay in `unexpectedPlayers`. Scores, map, population, rotation indexes and score tick are timestamped observations; no winner, ranking or result is derived. The last complete read survives a transient failure as stale and is discarded on process restart; the next scan rebuilds it from durable allocation ownership. The roster table never stores WDRCON payloads or credentials.

`GET /api/wardogs/lobbies/<id>` uses the existing JWT convention and permits a roster participant or CMP admin. It projects the latest cached observation without making status/player WDRCON calls; Join ID is separately cached after its first successful read. With no allocation it returns `none`; a first failed poll is `unavailable`; failed or overdue reads after success are `stale` with last-known values and timestamps. Missing/incorrect server association fails safely. Socket clients must present a valid JWT and pass the same lobby authorization before joining a private `wardogs:<id>` room. Change notices contain only the lobby ID; the frontend fetches the current authenticated HTTP state after a notice or reconnect. Cleanup closes the room and clears process-local data. `/prototype/wardogs` keeps mock scenarios by default; `?source=backend&lobby=<id>` opts into the backend read. Result confirmation remains mock-only.

The first public WARDOGS flow is CMP identity/party → `wardogs_beta9` queue (nine players; three active slots per faction; zero reserves; intact premades) → shared pending match and accept/decline/timeout → immutable accepted-player snapshot → Hybrid assignment → complete, insert-only WARDOGS lobby → transactional WARDOGS registry allocation → normalized join state → authenticated read model and `/wardogs/lobby/<id>` frontend. Queue formation does not require a server. After lobby creation, allocation requires approved, enabled WARDOGS registry state and a healthy probe from the last five minutes; it commits `servers.current_lobby_id`, the allocation history row, and `wardogs_lobbies.serverId` together. The lobby survives unavailable allocation, with an admin-only retry endpoint and no background loop. Registry ownership persists across restart and prevents double assignment. Explicit admin cleanup deletes the lobby and releases the allocation atomically; disconnects and failed read-only probes do not release it. The read model exposes `waiting_for_server`, `server_allocated_join_unavailable`, or `manual_join_available`. A failed Join-ID read never releases allocation. WDRCON URL and credentials remain administrative and are never used as player join details. Squad allocation and join paths retain their existing behavior.

## Referee result fallback and provenance

Use a CMP-generated `match_id` and distinct `attempt_id` to correlate an allocation, roster snapshot and any restart, even when WDRCON provides no stable round ID. A referee/admin with explicit permission marks the attempt ended, enters or confirms all three faction scores and ranking/tie disposition, attaches observation/evidence references, and submits a result draft. CMP stores who did it, when, source, server/build, roster revision, and any later correction/void event. Confirmation must be idempotent and reject stale or conflicting drafts; a correction creates an audited revision, not a silent overwrite. Manual confirmation need not imply the underlying score was server-authoritative.

Proposed state/provenance split:

| Status | Provenance | Meaning / rating eligibility |
| --- | --- | --- |
| `pending` or `needs_review` | `observed_snapshot`, `referee_entry`, or none | Incomplete/unconfirmed; **never** rated |
| `accepted` | `referee_confirmed` | Three-faction result explicitly approved; rating-eligible only when the current revision is completed, all placement groups are explicit, and the planned active roster meets the rating policy |
| `accepted` | `server_authoritative` | Allowed only when verified lifecycle, final scores, ranking and round identity are all available for this build; not currently enabled for WARDOGS |
| `void` or `cancelled` | actor/reason retained | No competitive result or rating |

Do not derive `accepted` from three finite live scores, a high score, a reset, a map transition, elapsed time, or an acknowledged end command. The backend—not the UI—enforces the state transition and rating gate. Existing Squad `save_completed_match` calls Elo immediately, so WARDOGS must not use that path unchanged. A referee workflow can operate while server observations are missing: display unknowns, allow evidence-backed entry, and keep the result pending until approved. The result revision must store authoritative placement groups before rating can run.

## Stack/runtime assessment

| Technology | Recommendation | Repository-specific reason and trigger to revisit |
| --- | --- | --- |
| Python + Flask | Keep | Existing auth, HTTP routes, server services and tests are usable; a WDRCON HTTP client fits without a language rewrite. |
| Flask-SocketIO + Socket.IO client | Keep | Existing lobby rooms/events support push to a WARDOGS store; introduce game-scoped payloads rather than changing Squad events. |
| Eventlet | Keep for Squad now; revisit **before high-volume production polling**, not before a read-only client/adapter skeleton | `backend/app.py` monkey-patches and sets `async_mode='eventlet'`; `live_roll.py`, `matchmaking.py`, `runtime.py` and `wiring.py` use greenlets/sleeps. Adding many long-running WDRCON polls inside this process could contend with Socket.IO and blocking DB/external calls. Start with bounded per-server reads, explicit timeouts, backoff, cancellation, and tests under the current runtime. Load/latency test before scaling; if unsuitable, migrate the whole backend async mode and greenlet call sites (for example to Flask-SocketIO threading plus supervised workers) with Squad regression tests. Do not mix an unplanned asyncio loop into monkey-patched code. |
| SQLite | Keep for current single-instance scale | `app_core.get_db_connection` opens per-operation connections; registry, queue state, history and Elo write to one DB, while runtime state persists periodically. Add transactional/idempotent result acceptance first. Revisit PostgreSQL when multi-process/multi-host writers, sustained concurrent polling/history writes, lock contention, recovery/HA or audit durability requirements exceed measured SQLite behavior. ## Recommended implementation sequence

1. Freeze DTO/capability/result status contracts and tests, including unknown/stale values and the manual gate. Define referee permissions, tie/incomplete policy and CMP match-attempt identity. Real-server lifecycle capture can continue **in parallel**.
2. Add game-aware registry configuration, credential handling, health/capability snapshots, allocation filters and safe release policy. Keep Squad records/health/join behavior unchanged; verify with existing tests.
3. Add a focused adapter selector and `SquadAdapter` wrapper around the existing bridge callback seam, preserving Squad outputs. Build a WDRCON client for already observed reads (capabilities, status, players, rotation), with auth, timeout, rate-limit/backoff, schema checks and sanitized logs.
4. The WARDOGS adapter and versioned lobby read model reconcile identities and surface unknown/observed connection, alignment and scores without running the Squad live-roll state machine. Immutable queue snapshots, Hybrid assignment, public beta queue, and accepted-match finalization are implemented; larger-capacity production policy remains later work.
5. Gate each WDRCON mutation independently after controlled effect/read-back evidence. Keep operator/manual actions where a gate fails. Provide game-specific join details and frontend transport; connect the existing WARDOGS Pinia model to normalized CMP DTOs while preserving `/prototype/wardogs` mock mode.
6. Implement referee draft/review/accept/void and audit/history, with transactionally idempotent result acceptance. This is the minimum useful completion path and **does not wait** for natural-end evidence.
7. Implement the designed WARDOGS-only rating calculation, immutable ledger, and deterministic replay from explicit result placement groups. Do not reuse two-team Elo by changing its input shape.
8. Only if later populated-server evidence proves authoritative end, final scores/ranking and stable round identity—including same-map restart—enable an automatic result source for supported builds. Otherwise retain the referee path indefinitely.

Sequence 2–4 can be developed alongside real-server investigation; 6 can be built alongside frontend/backend read integration after the result contract. The registry/DTO work precedes safe control, and accepted-result semantics precede ratings. No framework, database, SquadJS, Squad match-flow or production WDRCON change is made by this document.
