# CMP ↔ WARDOGS target architecture and reuse audit

Design audit, 2026-09-23. This remains an incremental target. The implemented slice includes [observation/capability contracts](../../backend/services/game_server_contracts.py), a [read-only WDRCON client](../../backend/integrations/wardogs/client.py), the [generic adapter boundary](../../backend/services/game_server_adapter.py), and a [WARDOGS adapter](../../backend/integrations/wardogs/adapter.py). A WARDOGS lobby read model and authenticated GET transport now exist; matchmaking and live allocation do not. It updates the older [Squad architecture audit](../../spikes/wardogs/WARDOGS_CMP_ARCHITECTURE_AUDIT.md): missing natural-end/winner evidence **does not block** a useful WARDOGS product, because the result can require a referee. Read the [capability matrix](CAPABILITIES.md) for the narrower status of each actual WDRCON operation. The WARDOGS [frontend feature](../../frontend/src/features/wardogs/) keeps isolated mock scenarios and can now opt into an authenticated backend read.

## What the repository does now

`backend/app.py` uses Flask-SocketIO with Eventlet; `backend/wiring.py` exposes HTTP and socket routes. `backend/services/queue.py` and `backend/matchmaking.py` accept queues and build two-team lobbies. `backend/app_core.py` selects per-server callbacks and passes them into `backend/services/live_roll.py`. Those callbacks use the Squad-specific HTTP client/normalizers in `backend/services/bridge.py`, the registry in `backend/services/server_registry.py`, and the bundled `squadjs/bridge-server.js` plus `squadjs/cmp/` modules. `live_roll.py` expects Squad layer transitions, two-side roster enforcement, and a winner/loser ticket record from `/round/best`; `app_core.save_completed_match` immediately invokes `backend/services/elo.py`. This is *not* a generic server adapter today.

`backend/services/state_persistence.py` serializes lobbies as JSON but restores only `team1` and `team2`. `backend/services/history.py` stores JSON team/result fields but its scored filter requires winner/loser tickets. `backend/app_state.py` declares `NvN` queue modes, two-team capacities and Squad map pools. `frontend/src/views/Lobby.vue`, `frontend/src/views/Results.vue`, `frontend/src/stores/state/lobbyState.js`, and `frontend/src/features/lobby/` consume the two-side contract. The WARDOGS feature instead has its own Match → Factions → Groups → Players model and local mock source.

## CMP competitive workflow reuse audit

The shared path should be CMP identity and persisted party → game-scoped queue mode → existing pending-match acceptance/cancel flow → game/mode-specific assignment and lobby builder. `backend/services/queue.py` already handles mode-keyed player lists, queue payloads, cancellation and acceptance without team semantics. `backend/matchmaking.py:start_match_acceptance` passes mode and player capacity; `finalize_pending_match` is the narrow branch because it supplies the builder callback. No second WARDOGS queue or acceptance implementation is needed.

CMP parties persist a code, leader and members in `active_groups`; group handlers prevent joins while queued and coordinate queue removal/cancellation on leave. This is enough to reuse party membership, but the queue stores only usernames and the acceptance snapshot stores only those usernames. Capture party identity and membership into the WARDOGS match group before any later membership changes; classify an ungrouped player as a one-person WARDOGS `solo` group. Never infer WARDOGS `clan` from party size alone.

Queue mode IDs remain globally unique and current Squad IDs are unchanged. Each configured mode now carries `game_type`; missing legacy metadata means Squad, while unknown game/mode pairs fail validation. The existing disabled-mode set therefore remains keyed safely by unique mode ID. Queue status includes game identity. Capacity checks count active lobbies and pending matches for the resolved game only; the legacy scalar is Squad capacity, and WARDOGS queue capacity is fixed at zero until join/allocation policy is approved. Queue rows persist mode IDs; unknown or removed IDs are skipped with a warning on restore, never reassigned. Pending acceptance remains process-local: startup clears it and retains valid queued players as unaccepted, with no timer resumed. The existing frontend queue store can merge server-supplied modes, but its built-in defaults and current home view are Squad-oriented.

The WARDOGS `wardogs_lobby` service already persists and validates its three-faction/group/role/readiness read model. It is not yet a matchmaking builder: no group-preserving faction assignment, capacity/overflow policy, queue entry, or allocation exists. The next implementation should define an immutable CMP party/solo queue-entry snapshot and the WARDOGS faction assignment contract before connecting a WARDOGS builder. Do not route WARDOGS through Squad `assign_teams`, map vote, lobby restore, live-roll or connection-detail assumptions.

## Minimal integration boundary

The first registry slice is now in `backend/services/server_registry.py`: existing rows migrate to `game_type='squad'`; WARDOGS records use `game_type='wardogs'`, the existing `bridge_url` as a **credential-free WDRCON origin**, and `wdrcon_secret_env` naming a server-side `CMP_WARDOGS_RCON_*` variable. Registration and probe require that variable to be configured; the password is never stored in SQLite or returned by an API. The existing `bridge_token_encrypted` field is **not** reused for WARDOGS: its `itsdangerous.URLSafeSerializer` provides signing, not confidentiality. Changing legacy Squad credential storage is separate work. WARDOGS registration/testing is restricted to admin endpoints; the existing Squad submission flow remains available. No WARDOGS join fields or join URL are synthesized.

For now, an administrator configures the secret in the backend process environment, then sends `{"game_type":"wardogs","display_name":"...","bridge_url":"https://host.example:7776","wdrcon_secret_env":"CMP_WARDOGS_RCON_SITE_A"}` to the existing authenticated `POST /api/admin/servers/test` and `POST /api/admin/servers` endpoints. The same admin health-check endpoint probes a registered record. The current frontend submission form remains Squad-oriented; no WARDOGS form or player-facing join link is implied by these backend APIs.

WARDOGS health reads only `/v1/capabilities` and `/v1/status`. The registry's `metadata_json` holds a sanitized normalized `capabilityStates` snapshot, build, limits and observation time. A successful status read is `observed`; players/rotation remain merely `advertised` until separately read; mutations stay `advertised` and lifecycle stays `unknown`. On probe failure the current health becomes `offline` and no fresh capability claim is made. The Squad boolean capability columns and health responses are unchanged and coexist with WARDOGS metadata. Default availability, pool capacity and allocation select only Squad records; explicit `game_type='wardogs'` selection exists at the registry service boundary but is not wired into matchmaking. The old single global-Squad fallback capacity remains when no Squad records exist. This is a registry seam, **not** a SquadAdapter or WARDOGS lobby integration.

`backend/services/game_server_adapter.py` now defines the `GameServerAdapter` observation protocol, a control-operation vocabulary, a safe adapter error, and `capability_is_usable`. Reads require an observed state to be reported as usable; controls require effect verification; lifecycle claims require semantic verification. A read may be called before it is observed because its successful call establishes that confidence. `WardogsAdapter` wraps `WDRCONClient` for capabilities, status, players, rotation and conservative lifecycle observation. It has no write dispatch. Its `require_control` gate rejects advertised-only operations and still rejects a verified operation because no WDRCON write implementation exists.

`server_registry.get_game_server_adapter_for_server` selects `WardogsAdapter` for a persisted `game_type='wardogs'` record using the existing restricted environment credential reference. It returns `None` for Squad, which explicitly means the existing `app_core.py` callbacks and `bridge.py` remain the active path. Unknown game types fail safely. A Squad wrapper/migration is optional later if a concrete call site needs one; there is no reason to force Squad through an incomplete adapter now. WARDOGS matchmaking/orchestration remains separate from this transport boundary.

Suggested typed contract (design notation, not code to introduce in this audit):

```text
capabilities() -> {name: {level, build, checked_at, evidence_ref}}
observe_status() -> ServerStatus(server_id, observed_at, health, map_config?, scores?, player_count?)
observe_players() -> [ServerPlayer(steam_id?, name?, observed_faction?, observed_at)]
observe_rotation() -> RotationSnapshot?                 # optional
request_control(command, actor, idempotency_key) -> CommandResult(requested, acknowledged,
                                                       observed_effect?, error?)
observe_lifecycle(cmp_attempt_id) -> LifecycleObservation(
    state=unknown|live_observed|completed_authoritative,
    source, observed_at, server_round_id?, final_result?)
```

`ServerStatus` and `ServerPlayer` are observation DTOs, not the CMP match model and not raw WDRCON objects. The CMP match holds faction IDs, group membership, active/reserve assignments, registered profile IDs and explicit player readiness; reconcile observations by validated Steam ID. Scores are timestamped and may be absent. `LifecycleObservation.unknown` is a first-class answer. `completed_authoritative` requires an independently established server result and round identity; no current WARDOGS evidence enables it. A `CommandResult.acknowledged` response never implies `observed_effect` or final result. Control methods are optional and must be checked by per-build capability *and* CMP permission; absence returns an unsupported/degraded result, not a fake success.

The contract prevents WDRCON JSON from leaking into CMP application state. `bridge.py` continues translating Squad `steamID`/numeric `teamID`, layer fields and `/round/best` through the existing Squad callbacks. WARDOGS maps Steam strings, named factions and status/rotation independently. Game-aware persistence and a join strategy are needed before a live WARDOGS lobby; rating abstraction can wait.

## Implemented WARDOGS application-state seam

`backend/services/wardogs_lobby.py` stores versioned CMP-owned WARDOGS lobby JSON in a dedicated SQLite table. The service validates exactly three canonical factions, stable group/player IDs, solo/squad/clan group type, active/reserve role, optional leaders/commanders, and explicit readiness. This is an internal seed/write service, not a public lobby creation or matchmaking route. User IDs, display identities and Steam links are roster snapshots owned by CMP; later lobby creation should populate them from CMP profiles. The record is durable across restart. It is separate from the Squad `active_lobbies` table, whose restore path remains two-team.

On demand, the read service combines that roster with normalized `WardogsAdapter.get_status` and `get_players` snapshots. A unique Steam ID is the only automatic reconciliation key. Registered players remain in their planned groups when absent; a successful empty roster marks linked players disconnected. No observation or a failed/stale read leaves connection and alignment unknown. Unmatched or ambiguous server players are listed as `unexpectedPlayers`, never inserted into the planned roster. CMP readiness is untouched. Scores, map and population are timestamped observations; no winner, ranking or accepted result is derived. The last complete server snapshot is held only in process memory so a failed read can report `stale`; it is discarded on restart. The roster table never stores WDRCON payloads or credentials.

`GET /api/wardogs/lobbies/<id>` uses the existing JWT convention and permits a roster participant or CMP admin. It returns only the normalized read model. With no server association it returns the roster with `observation.state=none`. With an explicitly associated WARDOGS registry server it performs bounded read-only observations on request; no background polling or allocation occurs. Missing/incorrect server association fails safely. The frontend's `backendDataSource.js` maps this payload into the existing Pinia match shape. `/prototype/wardogs` keeps mock scenarios by default; `?source=backend&lobby=<id>` opts into the authenticated backend read. Result confirmation remains mock-only.

The next production step is a controlled WARDOGS lobby creation/update workflow backed by CMP user profiles, followed by verified player join instructions and game-aware allocation before a connected live lobby. Keep Squad queue, lobby, live-roll, bridge, result and Elo paths separate.

## Referee result fallback and provenance

Use a CMP-generated `match_id` and distinct `attempt_id` to correlate an allocation, roster snapshot and any restart, even when WDRCON provides no stable round ID. A referee/admin with explicit permission marks the attempt ended, enters or confirms all three faction scores and ranking/tie disposition, attaches observation/evidence references, and submits a result draft. CMP stores who did it, when, source, server/build, roster revision, and any later correction/void event. Confirmation must be idempotent and reject stale or conflicting drafts; a correction creates an audited revision, not a silent overwrite. Manual confirmation need not imply the underlying score was server-authoritative.

Proposed state/provenance split:

| Status | Provenance | Meaning / rating eligibility |
| --- | --- | --- |
| `pending` or `needs_review` | `observed_snapshot`, `referee_entry`, or none | Incomplete/unconfirmed; **never** rated |
| `accepted` | `referee_confirmed` | Three-faction result explicitly approved; eligible for a *future* rating policy only after that policy exists |
| `accepted` | `server_authoritative` | Allowed only when verified lifecycle, final scores, ranking and round identity are all available for this build; not currently enabled for WARDOGS |
| `void` or `cancelled` | actor/reason retained | No competitive result or rating |

Do not derive `accepted` from three finite live scores, a high score, a reset, a map transition, elapsed time, or an acknowledged end command. The backend—not the UI—enforces the state transition and rating gate. Existing Squad `save_completed_match` calls Elo immediately, so WARDOGS must not use that path unchanged. A referee workflow can operate while server observations are missing: display unknowns, allow evidence-backed entry, and keep the result pending until approved. Disputes and tie-ranking policy need product rules before competitive acceptance.

## Recommended implementation sequence

1. Freeze DTO/capability/result status contracts and tests, including unknown/stale values and the manual gate. Define referee permissions, tie/incomplete policy and CMP match-attempt identity. Real-server lifecycle capture can continue **in parallel**.
2. Add game-aware registry configuration, credential handling, health/capability snapshots, allocation filters and safe release policy. Keep Squad records/health/join behavior unchanged; verify with existing tests.
3. Add a focused adapter selector and `SquadAdapter` wrapper around the existing bridge callback seam, preserving Squad outputs. Build a WDRCON client for already observed reads (capabilities, status, players, rotation), with auth, timeout, rate-limit/backoff, schema checks and sanitized logs.
4. The WARDOGS adapter and versioned lobby read model now reconcile identities and surface unknown/observed connection, alignment and scores without running the Squad live-roll state machine. Hybrid queue-entry/three-faction assignment policy remains later work once capacity/overflow rules are chosen.
5. Gate each WDRCON mutation independently after controlled effect/read-back evidence. Keep operator/manual actions where a gate fails. Provide game-specific join details and frontend transport; connect the existing WARDOGS Pinia model to normalized CMP DTOs while preserving `/prototype/wardogs` mock mode.
6. Implement referee draft/review/accept/void and audit/history, with transactionally idempotent result acceptance. This is the minimum useful completion path and **does not wait** for natural-end evidence.
7. Decide rating unit and tie policy, then add a WARDOGS-only rating consumer of accepted results. Do not reuse two-team Elo by changing its input shape.
8. Only if later populated-server evidence proves authoritative end, final scores/ranking and stable round identity—including same-map restart—enable an automatic result source for supported builds. Otherwise retain the referee path indefinitely.

Sequence 2–4 can be developed alongside real-server investigation; 6 can be built alongside frontend/backend read integration after the result contract. The registry/DTO work precedes safe control, and accepted-result semantics precede ratings. No framework, database, SquadJS, Squad match-flow or production WDRCON change is made by this document.
