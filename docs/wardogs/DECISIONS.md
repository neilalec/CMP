# WARDOGS decision log

| Date | Status | Decision | Rationale |
| --- | --- | --- | --- |
| 2026-09-23 | Accepted | WARDOGS support lives inside CMP. | Share the existing product and identity experience without copying the application. |
| 2026-09-23 | Accepted | Preserve existing Squad behavior. | Its two-side orchestration and results are established and should not change during WARDOGS exploration. |
| 2026-09-23 | Accepted | WARDOGS v1 uses Hybrid matchmaking. | Players can arrive solo, as squads, or as clan/team detachments. |
| 2026-09-23 | Accepted | Match → Faction → Group → Player is the competitive hierarchy. | Group identity must survive faction assembly and roster presentation. |
| 2026-09-23 | Accepted | Preserve premades where possible; use solos to fill gaps. | Population balance should not routinely split existing groups. |
| 2026-09-23 | Accepted | Represent active and reserve rosters. | Substitutes need a visible place without implying automatic moves. |
| 2026-09-23 | Accepted | Group leaders and faction commanders are optional. | Their selection and authority are not yet defined. |
| 2026-09-23 | Open | Match lifecycle and final result policy. | Populated natural end and same-map restart evidence remain incomplete. |
| 2026-09-23 | Accepted | WARDOGS v1 rates individual CMP accounts with pairwise three-faction Elo (`wardogs_rating_v1`). | A completed authoritative placement becomes the three faction-vs-faction outcomes. Use the arithmetic mean of each faction's planned active players, fixed K=24, start at 1000, and calculate every pair from the same pre-match ratings. |
| 2026-09-23 | Accepted | WARDOGS ratings include only the registered planned active roster, and only when all three factions have equal nonzero active counts. | The beta is three active players per faction. Reserves, observed presence, unexpected players and live faction alignment do not alter competitive membership. Unequal or incomplete rosters are unrated until a size-neutral policy is designed. |
| 2026-09-23 | Accepted | Pairwise ties score 0.5; score margin, premade size and party identity do not alter rating. | The authoritative placement/tie groups determine pair outcomes. Premades do not receive a persistent rating or modifier. |
| 2026-09-23 | Accepted | Only current authoritative `completed_win` or `tie` result revisions can produce WARDOGS rating events. | Incomplete, abandoned, void, cancelled and unconfirmed outcomes produce no rating. WDRCON observations never qualify. |
| 2026-09-23 | Accepted | WARDOGS rating correction uses deterministic full replay and an append-only, versioned event ledger. | A correction replaces the authoritative result input, then replay recomputes the corrected match and later matches from the initial rating. Previous events remain auditable and are superseded by replay generation; retrying the same revision is idempotent. |
| 2026-09-23 | Accepted | WARDOGS rating display starts with a numeric value and per-match delta; a leaderboard is deferred. | Keep rating generation independent from presentation. Do not add tiers or reuse Squad Elo fields. |
| 2026-09-23 | Implemented | Every completed WARDOGS result revision stores explicit ordered placement groups for all three factions; downstream rating consumes those groups and never sorts scores. | Explicit groups support normal placement, tie for first, tie for second, and three-way tie. Scores validate the submitted placement but do not define it. |
| 2026-09-23 | Not approved | Global N-team CMP refactor. | The target audit favors a minimum game-scoped boundary; no application-wide conversion or production refactor is authorized. |
| 2026-09-23 | Implemented | Deliver WARDOGS by verified capability, with explicit admin-confirmed results as the manual authority path. | Unproven lifecycle signals must not block useful matchmaking/roster features or be replaced by score/map/time heuristics. |
| 2026-09-23 | Accepted | Registry records carry explicit `game_type`; WARDOGS probe confidence lives in metadata beside legacy Squad capability columns. | Existing rows default to Squad and existing Squad health/selection semantics remain intact; no broad registry redesign is needed yet. |
| 2026-09-23 | Accepted | WARDOGS credentials use a restricted server-side environment reference; player join data is read-only and dynamically retrieved. | The existing signed `bridge_token_encrypted` serializer does not provide confidentiality. An environment reference avoids storing a powerful WDRCON password in SQLite; only the verified Join ID is exposed to players. |
| 2026-09-23 | Accepted | Use a small normalized observation protocol and a separate capability gate for controls. | WARDOGS reads go through `WardogsAdapter` and the existing WDRCON client. Advertised routes cannot enable writes; even a verified control state has no write implementation yet. Squad keeps its current callbacks and bridge path. |
| 2026-09-23 | Accepted | Persist WARDOGS planned rosters separately from Squad lobbies; keep WDRCON snapshots process-local. | The versioned WARDOGS table holds groups, roles, planned factions and explicit readiness. The read model merges optional server observations without overwriting that state. |
| 2026-09-23 | Accepted | Match observed players by unambiguous Steam ID and leave unexpected players outside the planned roster. | Display names are not stable identities. Connection and observed faction belong to the server snapshot; readiness belongs to CMP. Missing/stale reads remain unknown rather than erasing roster members. |
| 2026-09-23 | Accepted | Reuse CMP queue and match acceptance; branch to a game-specific assignment/lobby builder after acceptance. | Queue and acceptance services are mode-keyed and game-neutral through finalization. WARDOGS uses the existing acceptance callback and queue-mode assignment configuration; Squad keeps its builder. |
| 2026-09-23 | Accepted | Reuse CMP parties as WARDOGS premade inputs, then snapshot them into match groups. | CMP parties provide persistent code, leader and members but have no solo/squad/clan type; WARDOGS classification is separate match metadata. |
| 2026-09-23 | Implemented | Queue modes have globally unique IDs and explicit game identity; absent legacy metadata means Squad. | The existing disabled-mode set remains per-mode. Unknown game/mode combinations fail validation and never inherit Squad capacity or lobby creation. |
| 2026-09-23 | Implemented | Invalid persisted queue modes are skipped; pending acceptance is cancelled on restart while valid queued members remain. | Queue rows record mode IDs, whereas acceptance timers are process-local. Restore never moves unknown entries to Squad or resumes a stale countdown. |
| 2026-09-23 | Implemented | Accepted matches validate pending game identity before lobby creation. | Squad dispatches to its existing builder. WARDOGS requires a matching game/mode and derives assignment configuration from that mode. |
| 2026-09-23 | Implemented | WARDOGS matchmaking inputs are immutable snapshots created from accepted CMP identities and party state. | Party mutations after construction cannot alter entries. Partial parties contain only accepted players; stale/conflicting party state falls back to solos. CMP party existence does not classify a WARDOGS match group as squad or clan; that metadata must be supplied explicitly later. |
| 2026-09-23 | Accepted | Faction capacity and oversized-premade/overflow policy belong to WARDOGS matcher configuration. | Queue snapshots express matchmaking units only and contain no faction limits, assignment, reserve, or overflow decisions. |
| 2026-09-23 | Implemented | Hybrid v1 assignment preserves each premade as one indivisible entry; splitting is disabled. | An entry is wholly active in one faction, wholly reserve in one faction, or explicitly unassigned. |
| 2026-09-23 | Implemented | Assignment is deterministic and prioritizes intact premades, then active headcount balance, then solos filling gaps. | Stable entry IDs and canonical faction order resolve ties; the matcher uses no randomness or skill ratings. |
| 2026-09-23 | Implemented | Active and reserve capacities are explicit per-call configuration, not production assumptions. | Tests and future callers can supply appropriate capacities without enabling a production queue or server policy. |
| 2026-09-23 | Implemented | Entries that fit neither active nor reserve capacity remain explicit overflow. | A partial result carries each unassigned immutable entry and a reason; valid capacity shortage is not an invalid-input error. |
| 2026-09-23 | Accepted | CMP premade entries do not imply WARDOGS `squad` or `clan` classification. | Group display classification remains separate metadata and has no v1 assignment weight. |
| 2026-09-23 | Implemented | WARDOGS lobby creation requires a complete assignment. | Partial and invalid assignments return diagnostics without persisting a partial roster; no accepted player is silently dropped. |
| 2026-09-23 | Implemented | The first public WARDOGS mode reuses CMP queue, parties, and acceptance with config-driven 3×3 active slots and no reserves. | Parties must fit within one faction (three players). Match formation needs nine queued players but no allocated server. These beta values are not protocol limits. |
| 2026-09-23 | Implemented | Failed accepted-match finalization cancels pending acceptance and keeps valid participants in the same queue. | A controlled cancellation reason is emitted and no immediate retry is triggered, avoiding a repeated failure loop. A later queue event may retry. Successful lobby creation has no server allocation or join instructions. |
| 2026-09-23 | Implemented | Finalized CMP parties use neutral `premade` lobby type until classification is explicit. | Party size and CMP source kind cannot prove WARDOGS squad or clan identity. |
| 2026-09-23 | Implemented | Finalization persists CMP-planned groups, roles, and provenance without allocating a server. | Players start unready; connection and alignment remain read-only observations. The lobby records pending match, mode, snapshot source, capacity configuration, and creation time. |
| 2026-09-23 | Implemented | Finalized lobby creation uses a stable pending-match-derived ID and insert-only persistence. | A retry with the same roster and configuration returns the existing lobby; a conflicting retry cannot overwrite it. |
| 2026-09-23 | Implemented | WARDOGS allocation uses only approved, enabled WARDOGS registry servers with a healthy probe from the last five minutes. | One SQLite transaction reserves the server, records allocation history, and associates the persisted lobby. It never falls back to Squad. An unavailable server leaves the lobby intact; an admin can recheck health and retry explicitly. |
| 2026-09-23 | Implemented | WARDOGS allocation and WDRCON control are separate. | Allocation only changes CMP database state. Probe failures, disconnects, and reloads never release a reservation. Explicit admin lobby cleanup atomically releases it. |
| 2026-09-23 | Implemented | Manual WARDOGS Join By ID is the verified v1 join strategy. | CMP retrieves `/v1/server-id` dynamically from the allocated server and presents the tested Deploy → Community → Join By ID workflow. No direct-IP or Steam URI is assumed. A temporary Join-ID read failure leaves the server allocated and reports join unavailable. |
| 2026-09-23 | Implemented | A single periodic WARDOGS worker observes only allocated lobbies and keeps planned roster state separate. | Every 20 seconds it reads normalized status and players, reconciles by unambiguous Steam ID, and sends private lobby update notices for changed data. Unexpected players remain separate. The process-local last complete read stays visible as stale after failure; failures never release allocation. Scores, map, rotation indexes, and elapsed time cannot establish lifecycle or official results. |
| 2026-09-23 | Implemented | Only explicit admin confirmation creates an authoritative WARDOGS result. | Live observations may prefill but never finalize or choose a winner. Confirmed scores may differ from observed scores; the structured provenance records both, timestamp, actor, and divergence. Results are immutable after confirmation and survive restart. Ratings consume confirmed results only in a future milestone. |
| 2026-09-23 | Implemented | WARDOGS results use append-only revisions; the latest sequence is authoritative. | The original confirmation is revision 1 and migration preserves its provenance. Each correction requires an admin, reason, and expected current revision; it records the complete replacement and superseded revision. Ratings will consume the current authoritative revision, never raw observations. |
