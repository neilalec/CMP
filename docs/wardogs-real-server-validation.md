## CMP integration inspected

- The isolated client in `backend/integrations/wardogs/client.py` implements fixed bearer-authenticated GETs for `/v1/capabilities`, `/v1/status`, `/v1/players`, `/v1/rotation`, and `/v1/server-id`. It parses JSON with bounded response size and does not log remote exception text. The adapter exposes only reads; `require_control` always fails closed, even for advertised writes.
- The registry uses a numeric CMP server-record ID and an environment-variable name matching `CMP_WARDOGS_RCON_*`; the secret itself comes from the process environment. Its explicit probe reads capabilities then status. Allocation is a local transactional reservation using an approved, healthy registry record whose last health check is no older than 300 seconds; allocation itself does not contact WDRCON.
- A finalized CMP match creates its own lobby ID from the pending CMP match ID and stores the planned three-faction roster. The lobby remains CMP-owned; there is no WDRCON-derived phase transition.
- `backend/services/wardogs_live.py` polls allocated lobbies every 20 seconds by default (5 seconds in development; configurable from 2 to 3600). Each poll reads status then players. Complete snapshots are cached in process memory, keyed by CMP lobby ID and numeric registry ID, and sent to clients through CMP Socket.IO only when contents change or freshness needs emission. On failure, the last complete snapshot is retained and marked stale. CMP does not poll WDRCON rotation or Join ID in this worker.
- On lobby reads, CMP lazily fetches and caches the `/v1/server-id` value as the player-facing Join ID for that lobby/server allocation. The endpoint value is not stored as match identity. CMP maps planned players to observations by unique valid Steam ID; reported connected faction alignment is observational. The player's readiness field remains CMP roster state, not a WDRCON observation.
- Results are append-only and require an explicit authorized admin submission, including a three-faction placement for win/tie outcomes. Corrections require the current revision and a reason. Rating replay consumes the latest accepted revision; no server observation triggers completion, result confirmation, or rating.

The checked-in capability route list also advertises `/v1/audit`, health, config/catalog reads, and several write routes. CMP's WDRCON client does not call `/v1/audit`; no local endpoint specification was found to establish its event semantics. The advertised routes contain no websocket, SSE, webhook, or event-feed route. The recorder's `DERIVED CANDIDATE` records are local comparisons between polls, not server events.

**Transport caution:** the prior evidence used `http://199.115.74.113:9006`. Bearer authentication over plain HTTP is observable in transit. This run did not reuse that transport or credential. For another authenticated remote capture, use HTTPS or a protected tunnel before sending a bearer token.

## Classification and next evidence needed

**Proven enough for automation:** none of the server lifecycle/result signals. Existing safe automation is limited to bounded read polling, UI freshness notification, and CMP-owned allocation mechanics based on the current registry health/approval policy. These do not establish game lifecycle.

**Useful observational signals only:** map/config, population, faction score, rotation, and—when a populated roster and unique Steam IDs are captured—connection/faction alignment. Map changes, score resets, rotation movement, timer-like values, disconnects, and candidate feed records all carry false-positive risk for completion or restart. A missed poll or transient server/API failure creates false negatives or stale reads. Keep them out of result and rating triggers.

**Must remain manually confirmed:** match start/phase, natural completion, winner/tie and placements, corrected result, and any action with game-server write effects. No server write was attempted. The standalone spike `probe.py` has explicit mutation commands; its confirmation flag does not make a public server a safe test target.

For useful next evidence, configure a credential reference through the existing environment mechanism and provide a protected HTTPS/tunnel route. Capture repeated read-only snapshots during a populated match and across a naturally completed match, retaining timestamps and redacting Join IDs/player identifiers. A controlled same-map restart and any write-effect test require an explicitly designated isolated test server and an operator-approved window. Inspect the semantics of advertised `/v1/audit` from server documentation before relying on it.

Manual participant checks still needed: authenticated Play → queue → Match Accept → Match Room → Join By ID → observation → admin confirmation/correction → history, plus protected Squad screens. No auth bypass was attempted. No CMP implementation bug was reproduced; the evidence recorder did have a Join ID redaction gap, corrected as part of this evidence work.
